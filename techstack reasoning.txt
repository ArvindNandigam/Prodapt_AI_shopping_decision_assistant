We selected our technology stack based on the requirements of the problem and the prototype constraints rather than adding unnecessary complexity.

For the frontend, we chose Streamlit. Our application is primarily a data-driven interface consisting of search filters, product cards, comparisons, and AI recommendations. Streamlit allows us to rapidly build and iterate on this interface while keeping the frontend in Python. Compared with React or Next.js, it reduces frontend infrastructure and development overhead for this prototype.

For the backend, we chose FastAPI. It provides a lightweight REST API, integrates naturally with our Python-based AI pipeline, and gives us Pydantic-based request and response validation. It also keeps the frontend decoupled from the search and AI implementation.

For product data, we use DummyJSON for the prototype. It provides a sufficiently varied product catalogue containing information such as prices, ratings, stock, discounts, reviews, warranty, and return policies. We cache the catalogue so that external API availability does not become part of every user request.

For retrieval, we deliberately use deterministic in-memory filtering rather than an LLM or a heavyweight search engine. At prototype scale, the catalogue is small enough that filtering by category, price, rating, and text can be performed extremely quickly. This makes retrieval predictable and auditable. If the catalogue grows, the same interface can be moved to a dedicated search engine such as Meilisearch.

For AI reasoning, we use Claude through an API. We don't ask the LLM to search the catalogue. Instead, we first retrieve the relevant candidates and then give only those candidates to the model. This allows the LLM to focus on the task where it provides the most value: understanding trade-offs, comparing products, generating advantages and disadvantages, ranking candidates, and explaining the recommendation.

For storage, we use an in-memory cache for the prototype. At this scale, a persistent database would add complexity without providing significant value. For production, product data can move to PostgreSQL and session/cache state can move to Redis.

For testing, we use pytest and httpx for backend and API testing, with Playwright for end-to-end UI validation. For deployment, the prototype can be containerized with Docker Compose and later deployed to a scalable container platform.

Overall, our approach is:

simple at prototype scale, modular in architecture, and replaceable at production scale.

We can therefore replace individual components—such as the in-memory search with Meilisearch or the cache with PostgreSQL/Redis—without redesigning the entire application.
